# 2.7. Kiến trúc hệ thống

## 2.7.1. Kiến trúc tổng thể — `demo/2.7.1-kien-truc-tong-the.png`
Nguồn: `tools/gen_component.py`. 18 thành phần, 25 phụ thuộc, 5 gói (tầng). Tên thành phần trùng tên lifeline ở 2.5; "Máy chủ API (FastAPI)" là **gói** chứa 3 thành phần API.

| Tầng (gói) | Thành phần | Ghi chú |
|---|---|---|
| Tầng giao diện | Ứng dụng vỏ (WebView); Khung chat (Web/WebView); Trang quản trị | ĐA mục 2 "Nền tảng": khung chat ưu tiên điện thoại, nhúng WebView, mô phỏng bằng ứng dụng vỏ; trang quản trị dùng trên máy tính. React + TypeScript. Ứng dụng vỏ nhúng Khung chat và **truyền danh tính** cho Khung chat, Khung chat gửi tiếp tới API xác thực (CN01, 2.5.0) |
| Máy chủ API (FastAPI) | API xác thực (CN01); API hỏi đáp (CN02–CN06); API quản trị (CN07–CN09) | Python, FastAPI |
| Lõi RAG – luồng truy vấn | Bộ chuẩn hóa, viết lại câu hỏi (CN11); Bộ kiểm soát câu trả lời (CN14); Bộ nhớ đệm (CN13); Bộ truy xuất lai, Bộ xếp hạng lại (CN12); Bộ sinh câu trả lời | Bộ sinh câu trả lời kết nối LLM qua LangChain (ĐA mục Công nghệ) |
| Lõi RAG – luồng nạp dữ liệu | Bộ trích xuất (OCR), Bộ chia đoạn, Bộ lập chỉ mục (CN10) | rank_bm25 + thư viện tách từ tiếng Việt |
| Tầng dữ liệu | CSDL (PostgreSQL + pgvector); Kho tệp tài liệu | Bộ nhớ đệm lưu trong CSDL (`answer_cache`, `answer_cache_sources`); tệp gốc ở Kho tệp (`documents.storage_path`) |
| Bên ngoài | Dịch vụ LLM | GPT-4o-mini / Gemini / LLM mã nguồn mở |

Phụ thuộc chính:
- API hỏi đáp gọi 6 thành phần của luồng truy vấn theo thứ tự Hình 1.
- API quản trị gọi luồng nạp dữ liệu, Kho tệp và hủy bộ nhớ đệm (QT6).
- Mọi API kiểm tra phiên qua API xác thực: API hỏi đáp → API xác thực, API quản trị → API xác thực (khớp message "Kiểm tra phiên" ở 2.5.1–2.5.6b).

### Cấu hình thực nghiệm (bật/tắt từng cải tiến — ĐA mục 5, Bảng 6, Bảng 7)
- Mỗi cải tiến của Bảng 6 là một thành phần riêng ở 2.7.1. API hỏi đáp đọc **cấu hình thực nghiệm** (lưu bảng `app_config_overrides`, admin bật/tắt ở màn Cấu hình của trang quản trị; mô hình chọn từ `model_profiles`) gồm các cờ: chuẩn hóa không dấu/viết tắt, viết lại câu nối tiếp, `retrieval_mode = vector | bm25 | hybrid` (Bộ truy xuất lai chạy được từng nhánh riêng, đủ 3 cấu hình của Bảng 6 dòng 4), xếp hạng lại, bộ nhớ đệm, và chiến lược chia đoạn `fixed`/`legal`. Tắt cờ nào thì API bỏ qua thành phần đó.
- RAG cơ bản = `chunk_strategy = fixed`, `retrieval_mode = vector`, tắt các cờ còn lại. Mỗi lần đo chỉ bật thêm một cải tiến để đo đóng góp riêng, trên cùng kho (hai bộ đoạn cùng nằm trong `chunks`).
- Script đánh giá ngoại tuyến, với từng cấu hình:
  - Ba chỉ số truy xuất (Recall@k, Precision@k, MRR): gọi trực tiếp Bộ chuẩn hóa → Bộ truy xuất lai → Bộ xếp hạng lại (cùng mã, cùng CSDL) để lấy **k mã đoạn theo thứ tự**, rồi so `chunks.start_offset/end_offset` với phần văn bản gán nhãn theo định nghĩa đoạn liên quan ở `specs/2.6` (đoạn chứa trọn span). Không đi qua API vì API chỉ trả các nguồn đã trích dẫn.
  - Faithfulness, Answer relevancy, p50/p95, TTFT: gọi qua API hỏi đáp, đo thời gian phía client.
  - Kết quả lưu thành báo cáo, không cần bảng riêng.
- Mỗi lần đổi cấu hình thực nghiệm thì **xóa toàn bộ `answer_cache`**, để câu trả lời của cấu hình trước không lẫn vào số đo. Phép đo có/không có bộ nhớ đệm chạy trên cấu hình đầy đủ, hai lượt: lượt lạnh (đệm rỗng) rồi lượt nóng; tách nhóm bằng `messages.from_cache`. Không nạp tài liệu giữa các lượt đo.
- Cờ ở `app_config_overrides` áp dụng cho toàn hệ thống, nên thực nghiệm **chạy trên một máy chủ riêng** dùng bản sao cùng CSDL (cùng kho tài liệu, cùng hai bộ đoạn). Hệ thống phục vụ sinh viên luôn giữ cấu hình đầy đủ, hội thoại thật không lẫn vào số đo.
- Mỗi khóa chỉ dùng một trong hai cột: `value` cho giá trị thường, `encrypted_value` cho khóa bí mật; API cấu hình kiểm quy tắc này khi lưu.

## 2.7.2. Luồng nạp dữ liệu và luồng truy vấn (vẽ lại Hình 1 ĐA)
Hình 1 là lưu đồ; chương 2 vẽ lại thành **2 biểu đồ hoạt động UML**, giữ nguyên số bước để đối chiếu.

**2.7.2a Luồng truy vấn** (`demo/2.7.2a-…png`, 17 nút, 20 luồng):
1. (1) Gửi câu hỏi kèm lịch sử → (2) chuẩn hóa, viết lại. Nhãn giữ nguyên chữ Hình 1; ở mức cài đặt khung chat chỉ gửi mã hội thoại, API tự đọc lịch sử (2.5.1–2.5.3 msg 2, 5–6).
2. ◇(3) Ngoài phạm vi/chèn lệnh? [có] → tạo thông báo từ chối.
3. ◇(4) Có câu trả lời còn hạn trong bộ nhớ đệm? [có] → nút hợp nhất.
4. [chưa có] → (5) truy xuất lai, bỏ tài liệu hết hạn, bị thay thế (QT3) → (6) xếp hạng lại.
5. ◇(7) Đủ căn cứ? [không] → tạo thông báo từ chối, chỉ phòng ban.
6. [đủ] → (8) LLM sinh câu trả lời kèm trích dẫn, câu hỏi gợi ý.
7. ◇ Có trích dẫn hợp lệ? (**bổ sung so với Hình 1**, QT1) [không] → thay câu trả lời bằng thông báo không đủ căn cứ, chỉ phòng ban (khớp `alt` của 2.5.2). Lưu ý thứ tự: (8) và (9) **chạy chồng**, câu trả lời hiển thị dần trong khi sinh; ◇ này xét khi sinh xong, nhánh [không] gửi lệnh **thay câu trả lời đã hiển thị** (2.5.2). Biểu đồ hoạt động vẽ tuần tự để giữ số bước của Hình 1.
8. Nút hợp nhất (điểm nối R của Hình 1) → (9) trả về theo streaming.
9. (10) Lưu hội thoại; chỉ câu trả lời **mới sinh** có căn cứ mới vào bộ nhớ đệm (câu lấy từ đệm không ghi lại) → kết thúc.

**2.7.2b Luồng nạp dữ liệu** (`demo/2.7.2b-…png`, 13 nút, 14 luồng):
1. (A) Nạp tài liệu chính thức và thông tin kèm theo → (B) trích xuất, OCR bản scan.
2. ◇ Là bản scan? [có] → (C) quản trị viên kiểm tra.
3. (D) Chia đoạn Chương – Điều – Khoản (và chia cố định cho mốc so sánh), gắn khóa, ngành, năm học, ngày hết hạn → (E) lập chỉ mục BM25 + vector.
4. ◇ Cập nhật phiên bản cho bản cũ? [có] → (F) ngừng dùng bản cũ, hủy câu trả lời liên quan; [không] → hủy câu trả lời đệm có nguồn cùng nhóm tri thức (**bổ sung so với Hình 1**, QA-3) → kết thúc.

Nhánh của ◇ này do quản trị viên chọn: thao tác "Cập nhật phiên bản" (CN08, 2.5.5) là [có], nạp mới (2.5.4) là [không].

**Lựa chọn trình bày:**
- Không vẽ phân làn (swimlane). Hình 1 cũng không có làn, và tên hành động đã nêu người thực hiện (bước (1) Sinh viên; (A), (C) Quản trị viên; (8) LLM). VP chưa có mẫu XML cho làn để sinh tự động; nếu GVHD yêu cầu thì thêm làn trực tiếp trên VP.
- Kho dữ liệu (Bộ nhớ đệm, CSDL) không vẽ thành nút, vì UML activity tập trung vào luồng điều khiển; thao tác đọc/ghi nêu trong tên hành động, chi tiết ở 2.5.
